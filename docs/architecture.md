# architecture

## the short version

Astro builds every page to static HTML at build time. Cloudflare Workers serves `dist/` as [static assets](https://developers.cloudflare.com/workers/static-assets/). No code runs per request for pages.

```text
Markdown + .astro ──astro build──▶ dist/ ──Workers Builds──▶ Cloudflare edge ──▶ www.harrisonjennings.au
        ▲
design/tokens.json ──scripts/build-tokens.mjs──▶ src/styles/tokens.css
```

## pieces

- **Pages** (`src/pages/`): one file per route. Trailing slashes are always used (`/blog/`), and `wrangler.jsonc` sets `html_handling: auto-trailing-slash` to match, so there are no redirect chains.
- **Content** (`src/content/`): posts and pages in Markdown, topics and projects in YAML. `src/content.config.ts` holds the schemas, so bad frontmatter fails the build. Posts publish at `/blog/<slug>/` and topics at `/blog/topic/<id>/`. See [content.md](content.md).
- **Components** (`src/components/`): each has scoped styles that read tokens only. Behaviours live in `src/scripts/` and are imported by the component that needs them, so Astro bundles them once per page.
- **Tokens** (`design/tokens.json`): the brand's single source of truth. `npm run tokens` writes `src/styles/tokens.css` (ignored by git, rebuilt before `dev`, `build` and `check`). Dark is on `:root` and `[data-theme="dark"]`; light only under `[data-theme="light"]`.
- **Theme**: dark on every first visit, whatever the device is set to. The nav's sun/moon toggle (`ThemeToggle.astro`, `src/scripts/theme.ts`) switches theme and saves it in `localStorage` (`hj-theme`), a functional setting outside the consent banner. A tiny inline script at the top of `<head>` in `Base.astro` applies the saved theme before first paint, so there's no flash; the Content-Security-Policy will need its hash.
- **Layout**: one column shared with the nav. `.shell` holds the nav pill (`--container` wide, `space-16` gutters); `.column` holds page content, starting under the nav's logo and ending under its button. Breakpoint 760px. On the home page and the 404 the nav floats over the first screen (`<Base float>`); elsewhere it sits 16px from the top. Both stay in view while scrolling, so the compact state (after 80px) is seen. Hovering doesn't reopen it (the links would move under the pointer); keyboard focus does.
- **Fonts**: Martian Mono and Schibsted Grotesk, variable, Latin subset, as woff2 in `public/fonts/`, with `font-display: swap`. Both are preloaded in `Base.astro`: Schibsted for body text, Martian Mono for the hero headline.
- **Home page** (`src/pages/index.astro`, `src/components/home/`): the hero (signal field on a canvas, `src/scripts/field.ts`), what I do, built and shipped (tabs, `switcher.ts`), what people are saying (`ticker.ts` from five quotes), latest posts and the booking band. On phones the card rows swipe sideways with arrow buttons (`swipe.ts`). Every behaviour has a still state under reduced motion.
- **Blog** (`src/pages/blog/`, `src/components/blog/`): the index and topic pages share one template (header, topic chips, posts by year); a post has its header, the text with "on this page" (`toc.ts`), the published line, the author panel and "keep reading". The rules (keep reading, which headings go in "on this page", grouping by year) are plain functions in `src/lib/blog.ts`. Wording lives in `src/content/blog.yaml`. No booking band on blog pages.
- **Projects** (`src/pages/projects/index.astro`): every project from `src/content/projects.yaml` by `order`, each with a large still screenshot (never a link, no scroll effect), its facts and links; archived projects follow as quiet rows once there are any.
- **Feeds** (`src/lib/feed.ts`, `@astrojs/rss`): `/rss.xml` for every post and `/blog/topic/<id>/rss.xml` for each topic page, as raw XML with no stylesheet (Chrome removes XSLT on 17 November 2026). People reading in a browser get `/rss/`, a normal page that explains the feed and copies its address (`CopyButton`, `copy-text.ts`); every "rss feed" link goes there, and topic pages link to their row (`/rss/#topic-<id>`). Every page's `<head>` names the feed (`<link rel="alternate">`); topic pages add their own. Migrated posts keep their WordPress guid (`https://www.harrisonjennings.au/?p=<wpId>`), and `/feed/` 301s to `/rss.xml`, so subscribers carry over without old posts arriving again. Items carry the description, not the full text; when an item is opened, feed apps show the description and a link to the full post.
- **Legal pages** (`src/pages/[page].astro`): the privacy policy and terms of use from `src/content/pages/*.md`, at `/<file name>/`. One template: the date and a link to the other page, "the short version" from a `summary` list, the text beside "on this page" (h2s only), and a contact line. `::cookie-settings` in the Markdown places the button that opens the cookie preferences, and `::cookie-table{category="…"}` builds a category's cookie table from `src/content/consent.yaml`, the same list the preferences dialog shows, so the two can't disagree.
- **Share cards** (`src/lib/og/`, `src/pages/og/[...path].png.ts`): a 1200 × 630 PNG per page, rendered at build to `/og/<path>.png` and named in `og:image` and `twitter:image` by `Base.astro`. Variants: home (also every page without its own: the legal pages and the 404), post, page (blog, topics, projects, rss) and project (rendered, but no page uses it until projects get pages of their own). Satori lays each card out as SVG with the brand fonts and sharp turns it into a PNG; the ember clouds are plain SVG gradients underneath. Satori can't read variable fonts, so the cards use static instances of the site's fonts in `src/assets/fonts/` (`scripts/build-og-fonts.py`). Martian Mono titles are broken into lines by character count (it's monospaced), so the brick stop always follows the last word. Dark only. A post's `socialImage` replaces its card.
- **Markdown** (`astro.config.mjs`, `src/lib/markdown/`): `@astrojs/markdown-remark` runs our plugins on every post and page. remark: callouts (`:::note`, via remark-directive), `::cookie-settings`, `::cookie-table`, text directives back to text (so "4.53:1" or "10:30" in a sentence stays as written), `{nozoom}`, reading time. rehype: h5/h6 to h4, framed tables with number columns, links to other sites opening in a new tab (with `noopener` and a hidden note for screen readers), figures (reading each local image's size with sharp, so portrait images are capped before they load), and the code block wrapper. Code is highlighted at build by Shiki with a theme whose colours are the code tokens (CSS variables); every block carries `data-theme="dark"`, so code keeps the dark treatment on light pages too. Shiki also gets a small Velocity grammar, and a transformer for file names, highlighted lines and shell prompts. MDX posts get `<Figures>` and `<YouTube>` without importing them. Images are responsive (`image.layout: 'constrained'`); the image viewer (`lightbox.ts`) loads the largest size only when it opens. Post styles are in `src/styles/prose.css`.
- **Drafts**: shown in `npm run dev` only. The end-to-end tests build with `INCLUDE_DRAFTS=true`, so the draft formatting reference is tested; CI checks the production build has no drafts. Deploy with `npm run deploy` (or Workers Builds), which rebuilds without drafts, never by running `wrangler deploy` straight after the tests.
- **Consent** (`src/components/Consent.astro`, `src/scripts/consent.ts`, wording in `src/content/consent.yaml`): the banner shows on every page until a choice is made; "manage preferences" and every "cookie settings" button (`[data-consent-preferences]`) open the preferences dialog. CookieConsent v3 (self-hosted, `vanilla-cookieconsent`) keeps the choice in `cc_cookie` with a revision and a consent ID, and clears analytics and advertising cookies when they're refused; its own interface is never shown, because the design's banner is a labelled region (not a modal) with `role="switch"` toggles, which its markup can't give. Raising `revision` in `consent.yaml` asks everyone again.
- **Google Consent Mode and Tag Manager** (`src/layouts/Base.astro`, `src/lib/tag-manager.ts`): an inline script in `<head>` sets every optional signal to denied, applies a returning visitor's saved choice, and pushes the page's data layer keys (`page_name`, `page_type`, `post_author`, `categories`, `tags`, `post_id`, as the WordPress site did) before Tag Manager loads. The script is identical on every page, so the Content-Security-Policy allows it by one hash; each page's keys sit in a JSON block just before it (`data-page-layer`), which doesn't run. Each choice sends `gtag('consent', 'update', …)` (analytics → `analytics_storage`; advertising → `ad_storage`, `ad_user_data`, `ad_personalization`) and a `cookieConsentInteraction` event. Tag Manager loads first-party from `measure.harrisonjennings.au`: the Live environment on production builds (`main` on Workers Builds), the Testing environment on branch previews (it sends only to the testing GA4 property), and nothing locally or in the tests. `TAG_MANAGER_ENV` (`live`, `testing`, `off`) overrides it. In the container, every hit carries an `environment` label from two chained Lookup Tables (`lookup - environment`: `Testing` in preview mode, where the environment name is a generated one, or on the Testing environment; `Live` otherwise), and the server container sends it to the production or testing GA4 property by that label. The container has no Custom JavaScript variables or Custom HTML tags, which the Content-Security-Policy doesn't allow.
- **Consent log** (`src/worker/`, `migrations/`): the only Worker code (with the CSP report endpoint), run for `/api/*` alone (`run_worker_first`). `POST /api/consent` checks the request comes from the site's own pages (by `Origin`, which only stops other sites' pages), reads at most 2 KB, checks the record hangs together (the current revision; the necessary category always; every category for accept all, only necessary for reject all; a path of URL characters) and writes one row per choice to D1 (`consent_log`): consent ID, when, the page path, country and region, user agent, each category, the action, the revision, and whether it came from production or a preview. The IP address is stored only as an HMAC-SHA256 hash keyed with the `CONSENT_IP_KEY` secret, so it can be matched against an IP someone gives but not read back. Rows are never updated: a change is a new row, so the history stays. A daily Cron Trigger (`src/worker/retention.ts`) deletes consent records 12 months after they were received, and CSP reports 90 days after they were last seen; the privacy policy states the consent period.
- **Booking** (`src/scripts/booking.ts`, the calendar from `BOOKING_URL`): nothing from Cal.com loads with the page. In the booking band, "view availability" opens the calendar inside the band and only then loads Cal.com's embed. Every "book a call" (nav, phone menu, hero, footer) links to `/#book`: on the home page it scrolls to the band and opens its calendar; on any other page it opens the same calendar in Cal.com's modal, with focus moved onto the modal's close button and back to the link when it closes. Never put `data-cal-link` on our own elements: Cal.com's embed turns them into popup triggers. Cal.com's events go to the data layer as `{ event, cal_raw_event }` (its housekeeping events left out), so Tag Manager's `meeting_booking` tag fires on `bookingSuccessful` as before.
- **Headers** (`public/_headers`): security headers on every response, and long immutable caching for hashed assets and fonts.
- **Content-Security-Policy** (`src/lib/csp.ts`, `src/lib/csp-build.ts`): the sources for each directive live in `csp.ts`. After every build, the `csp()` integration hashes each inline script in `dist/` (the theme and consent scripts, and the Tag Manager loader on builds that load it) and adds `Content-Security-Policy-Report-Only` and `Reporting-Endpoints` to the `/*` rule in `dist/_headers`. It fails the build on an inline event handler or a header line over Cloudflare's 2,000 characters. Component scripts always ship as files (`vite.build.assetsInlineLimit` in `astro.config.mjs`), so they're covered by `'self'`. Browsers send violations to `POST /api/csp-report` (`src/worker/csp-report.ts`), which keeps one row per distinct violation in `csp_report`, in the consent database, with a count, without query strings. Cloudflare adds two scripts of its own: the Web Analytics beacon (allowed) and Bot Fight Mode's inline JavaScript Detections scripts (a loader and the script it writes into a hidden frame), which change on every request, so they're left refused and their reports are dropped. Report-Only blocks nothing; switching to `Content-Security-Policy` is a one-word change in `cspHeaders()`, once the reports are clean.
- **Structured data** (`src/lib/structured-data.ts`): one JSON-LD graph in every page's head. Every page names the WebSite and the Person (Harrison, with LinkedIn and GitHub as `sameAs`); the home page adds the ProfessionalService and what it offers (from `services.yaml`); posts a BlogPosting (headline, description, share card, dates as midnight in Melbourne with the offset, author, topics); the blog a Blog, topic pages a CollectionPage; every inner page its breadcrumbs. Pages pass theirs to `Base` as `structuredData`. JSON-LD doesn't run, so the CSP needs no hash for it.
- **Sitemap** (`@astrojs/sitemap`, `src/lib/sitemap.ts`): every built page, with `lastmod` where there's a real date: a post's `updated` or `published`, the blog and topic pages from their newest post, the legal pages from `updated`. Pages kept out of search (`noindex`) carry no canonical address.
- **Redirects** (`public/_redirects`): one explicit 301 per old WordPress post and category URL, plus the old sitemap and feed URLs. No wildcards; the `redirects` end-to-end test checks every rule.
- **404**: `src/pages/404.astro` builds `404.html`, which Workers serves for any unknown path (`not_found_handling: 404-page`). It's the one inner page with the ember clouds and the bouncing dot (`<Logo loading>`), with the latest three posts; wording in `src/content/not-found.yaml`. WordPress-only URLs (`?p=` shortlinks, `wp-content` uploads) are left to lapse.
- **Design system** (`design-system/`): `design.harrisonjennings.au`, a second Astro site in an npm workspace, built from the site's own components, styles, tokens and Markdown pipeline (imported, never copied) and deployed as its own Worker. See `docs/design-system.md`.

## tests

`npm run verify` runs both suites after format, lint and type checks; `npm run lighthouse` runs Lighthouse. In GitHub Actions, two orchestrator workflows call the rest as reusable workflows:

- **🛠️ CI Orchestrator** (`ci-orchestrator.yml`), on every pull request and on `main`: **quality** (`quality.yml`: format, lint, types, unit tests, the production build, no drafts in it), **end-to-end** (`end-to-end.yml`: Playwright, in parallel with quality, with the site in Chromium, the site in WebKit and the design system on separate runners, each in Playwright's own container image at the lockfile's version, and one **Playwright** check that passes when all three do), **lighthouse** (`lighthouse.yml`: the home page, the blog, a post and projects, three runs each, failing below 95 on performance, accessibility, best practices and SEO; see `lighthouserc.json`), and **codeql** and **dependency review**. The merge rule requires quality, end-to-end and lighthouse. `@lhci/cli` runs through `npx` at the version in the `lighthouse` script, not as a dependency, because its own dependencies carry security advisories.
- **🚀 CD Orchestrator** (`cd-orchestrator.yml`): Cloudflare does the deploying; this runs around it. It starts when Cloudflare finishes a build: each Worker posts a "Workers Builds: <Worker>" check on the commit it built, and GitHub runs the orchestrator on that check (`check_run`), so nothing waits or polls. The site and the design system go through the same three workflows, with their own scripts and environments. For a branch, the build is recorded as a GitHub deployment (`preview-deployment.yml`; Preview, Design system preview). For `main`, that exact version is smoke-tested through its preview address with the Access service token (`production-version.yml`, running `scripts/smoke-test.sh` or `scripts/design-smoke-test.sh`; Bot Fight Mode challenges GitHub's runners on the real domains), then the live domain is checked and a deployment recorded (`production-live.yml`, running `scripts/live-check.sh` or `scripts/design-live-check.sh`; Production, Design system). On a pull request it also posts the preview link (`preview-link.yml`), which doesn't wait for a build. Deployments are recorded through the API against the built commit's branch (`scripts/record-deployment.sh`), because on a `check_run` a job's own commit is `main`'s latest. Running it by hand (Actions → 🚀 CD Orchestrator → Run workflow) repeats `main`'s checks for a branch's latest commit. A `check_run` workflow runs in `main`'s context, so GitHub lists each run, and its jobs' checks, on `main`'s newest commit at the time, whichever commit Cloudflare built: a branch's preview run shows among `main`'s checks, and a failed preview build would show a ✗ there though `main` is fine. Each run's title names the Worker and branch it's for, and the deployment records are against the right commit. `scripts/version-url.sh` and `scripts/preview-url.sh` are shared.

- **Unit** (`tests/unit/`, Vitest, `npm run test`): the pure logic. Consent (the Consent Mode signals, checking a posted record, which Tag Manager environment a build loads, the IP hashing, and the log handler against a fake D1), the CSP (the policy, finding and hashing inline scripts, adding it to `_headers`, reading both report formats, and the report handler against a fake D1), the share cards (title sizes and line breaks, image paths, and each variant rendering to a 1200 × 630 PNG), the feeds (addresses, items, and a migrated post keeping its WordPress guid), `src/lib/posts.ts` (slugs, URLs, drafts, newest-first order, which topics earn a page) with `astro:content` mocked, and `buildTokensCss` from `scripts/build-tokens.mjs` against both the real `design/tokens.json` and small fixtures for the edge cases (fallback values, font paths, bad and duplicate names). `vitest.config.ts` uses Astro's Vite config, so `import.meta.env` behaves as it does in a build.
- **End-to-end** (`tests/e2e/`, Playwright, `npm run test:e2e`): builds the site, applies the D1 migrations to a local database, then tests `dist/` served by `wrangler dev` on port 8790 (with a test `CONSENT_IP_KEY`), so `_headers`, trailing-slash handling and the 404 page behave as they do on Workers. Page lists come from the built sitemap, so new pages are covered automatically. Two projects: desktop Chromium runs everything; WebKit on an iPhone runs the specs that drive the page (not the request-level ones), leaving out tests tagged `@keyboard` (Tab, which WebKit gives only to form fields by default) and `@desktop` (the desktop nav).
  - `pages`: every sitemap page returns 200; an unknown path returns 404, with the 404 page for browser page loads (Cloudflare sends other requests a bare "Not found").
  - `menu`: at phone width the menu opens with focus on its first link from the keyboard, or on the menu itself from a tap or click (nothing shows); a focused link takes the hover treatment, not the ring, keeps focus out of the page behind it, and closes on Escape or the close button with focus back on the menu button. It's a native modal `<dialog>`, so Tab steps out to the browser's own controls after the last item and back in from the first; the test allows that and fails if focus reaches the page.
  - `motion`: under `prefers-reduced-motion: reduce`, no animation runs on load or hover, the logo stays at rest, and the page is pixel-identical half a second apart.
  - `headers`: every rule in the built `dist/_headers` (including the CSP the build adds) is checked against a real response from a matching path.
  - `csp`: every sitemap page, the cookie banner and preferences, and a post's video run with no CSP violations; a script outside the policy is caught (so a clean run means something); each page's data layer keys still arrive; the report endpoint stores a report and refuses junk. Tag Manager isn't loaded in tests: its violations show up in the reports.
  - `nav`: the nav's position (floating on the home page and the 404, 16px down elsewhere, in view while scrolling), compacting after 80px and reopening on hover, the current-page underline, and the footer logo drawing when it comes into view.
  - `blog`: the index (posts by year, the RSS link, no booking band), and on the formatting reference: the header and reading time, "on this page" marking the section being read (a closed panel on phones), h5 shown as h4, callouts, figures, number columns and footnotes, code blocks (file name, highlighted lines, copy without prompts, edge to edge on phones), the image viewer (zoom, stepping, Tab kept inside, Esc and focus return), `{nozoom}`, and YouTube loading only on play.
  - `home`: the hero, the scroll cue's fade, level tools lines in what I do, the project tabs by click and keyboard, the testimonials (still under five, moving with a working pause button from five), the phone swipe rows and stacked hero buttons, nothing third-party on load, and the booking calendar opening in place and only then requesting Cal.com.
  - `projects`: numbered entries with their facts and links, a screenshot that isn't a link, and no "archived" section until a project is archived.
  - `rss`: `/rss.xml` is raw RSS with no stylesheet, `/feed/` 301s to it, every page names it in `<head>`; the `/rss/` page copies the full address (and drops "https://www." on phones) and lists the latest posts.
  - `legal`: the privacy policy's date, link to the terms, short version, cookie settings button and h2-only "on this page"; the terms' "Effective" date and no short version.
  - `not-found`: the 404's links and latest posts, the dot bouncing (and resting under reduced motion), never clipped.
  - `crawl`: every URL the WordPress site published or Google knew about (`tests/e2e/fixtures/wordpress-urls.json`) answers 200 or a single 301 to a page answering 200; WordPress-only addresses (`/wp-json/`, `/wp-admin/`, uploads) are a real 404.
  - `redirects`: every rule in `public/_redirects` is an explicit path (no wildcards) that returns one 301 to a page answering 200.
  - `consent`: on a first visit the banner shows on every page with everything optional denied and nothing sent anywhere; "accept all", "reject non-essential" and saved choices set the right Consent Mode signals, are logged (one request, a 204 from the local D1) and are remembered; the dialog's focus, Esc and focus return; the footer's "cookie settings"; the phone layout; and axe on the banner and dialog in both themes. Every other spec starts with a choice already made (`tests/e2e/consented.ts`), so the banner doesn't cover what they click.
  - `structured-data`: every sitemap page has one JSON-LD graph with the WebSite and Person; pages in search have a canonical address matching the page, pages kept out have none; breadcrumbs end at the page; a post's BlogPosting matches its h1 and address, with Melbourne dates (time zone included, as Google asks) and a real share image; every post has a sitemap `lastmod`.
  - `share`: each page names its card (its own, or the home card) in `og:image` and `twitter:image`, and the card is a 1200 × 630 PNG.
  - `theme`: dark on a first visit even when the device prefers light; the toggle switches, relabels and is remembered on the next page.
  - `a11y`: an axe scan (WCAG 2.2 A and AA rules) of every page and the 404 page, in dark and light (chosen through `hj-theme`, as the toggle does).

Run `npx playwright install chromium webkit` once before the first end-to-end run. The smoke test (`scripts/smoke-test.sh <base URL>`) works against any copy of the site: production, a local `npm run preview`, or the end-to-end server.

## deploying

- **Builds:** Cloudflare Workers Builds builds every push, with the npm version in `package.json`'s `packageManager` (its build image would otherwise use an older npm than the one that writes the lockfile, and reject lockfiles that one accepts). `main` deploys to production; any other branch gets its own preview URL on `workers.dev`, behind Cloudflare Access. The production Worker has no public `workers.dev` address: `www` is served through a Workers Route, and a redirect rule sends the bare domain to `www`.
- **After each deploy:** the 🚀 CD Orchestrator waits for Cloudflare's production deploy, smoke-tests that exact version through its preview address (`scripts/smoke-test.sh`, using an Access service token from the repository secrets), checks the live domain, and records the deployment. On pull requests it comments the preview link and records a Preview deployment. It does the same for the design system (smoke test `scripts/design-smoke-test.sh`, live check, Design system and Design system preview deployments), for the commits Cloudflare builds it for. Every script that reads Cloudflare's checks picks them by Worker name.
- **The design system** deploys from its own Worker, `harrisonjennings-au-design`, with `design-system/` as its root directory and build watch paths, so it builds only when something it shows changes: see `docs/design-system.md`.
- **Rolling back:** redeploy the previous version from the Worker's deployments in Cloudflare. Every deployed version is kept.
- **Data:** D1 holds the consent log and CSP reports, with the schema in `migrations/` (`npx wrangler d1 migrations apply CONSENT_DB --remote`). Previews write to their own database and store no IP hash. The Worker's one secret is `CONSENT_IP_KEY`, the HMAC key for consent records, set in production only.
- **Protection:** a Cloudflare rate-limiting rule covers `POST /api/*`, and Bot Fight Mode is on.

## what's coming (and where it goes)

- **Content-Security-Policy, enforced:** after cutover week, once the reports are clean (Tag Manager's Custom JavaScript variables and Custom HTML tag removed or replaced).

Never route every request through Worker code (`run_worker_first: true`). On the free plan, once the daily request cap is hit those requests fail instead of falling back to the static page.

## rules of thumb

- Prefer build time over request time. If something can be computed when building, it should be.
- No client framework. If a component needs more than a small script, discuss it first.
- No new colours or sizes outside `design/tokens.json`.
